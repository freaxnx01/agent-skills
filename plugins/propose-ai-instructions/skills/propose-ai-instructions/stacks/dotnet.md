# propose-ai-instructions — heuristics for `dotnet` / `justfile`

Machine-readable rules consumed by `SKILL.md` Step 4. All pattern fields are regex.

This file applies to **every `dotnet-*` flavour** (currently `dotnet-blazor` and `dotnet-webapi`) — the lookup in SKILL.md Step 1 strips the `-<flavour>` suffix and falls back to this file. The upstream target is `_partials/dotnet-core.md` (the canonical source — flat overlays are regenerated by `scripts/build-stacks.sh`).

---

## generic_tools

Commands whose presence in a recipe body does **not** disqualify a recipe. A recipe whose entire body consists only of these is a promotion candidate.

```yaml
generic_tools:
  # .NET
  - dotnet
  - dotnet ef
  - dotnet format
  - dotnet watch
  - dotnet test
  - dotnet build
  - dotnet run
  - dotnet restore
  - dotnet list
  - dotnet publish

  # Containers
  - docker
  - docker compose        # v2 plugin form
  - docker-compose        # legacy binary form

  # Git ecosystem
  - git
  - gh
  - git-cliff

  # just itself (recipes can invoke other recipes via `just <name>`)
  - just

  # Networking / probing
  - curl
  - wget

  # Shell built-ins and POSIX basics (no disqualification)
  - echo
  - printf
  - mkdir
  - rm
  - cp
  - mv
  - find
  - grep
  - sed
  - awk
  - cut
  - sort
  - uniq
  - head
  - tail
  - cat
  - sleep
  - mktemp
  - test
  - pkill
  - until
  - if
  - for
  - while
  - case
```

Recipe dependencies in justfile are native (`release-auto: bump-auto release`) — no `$(MAKE)` recursion to allowlist.

### Conditional allowlist (only inside `[windows]`-attributed recipes)

These are PowerShell built-ins and types. They are **legitimate** when the recipe carries the `[windows]` attribute (cross-OS recipe pair) and **disqualifying** otherwise.

```yaml
windows_tools:
  - pwsh
  - powershell
  - powershell.exe
  - Get-Content
  - Set-Content
  - Get-ChildItem
  - Remove-Item
  - Copy-Item
  - Move-Item
  - Test-Path
  - New-Item
  - Start-Process
  - Start-Sleep
  - Write-Output
  - Write-Host
  - Write-Error
  - ForEach-Object
  - Where-Object
  - Select-Object
  - "\\[xml\\]"
  - "\\[version\\]"
  - "\\$ErrorActionPreference"
```

The classifier checks the recipe's attributes (parsed in SKILL.md Step 3). If `[windows]` is present, `windows_tools` entries do not disqualify. Outside a `[windows]` recipe, they fall through to `project_markers` and disqualify.

## project_markers

Any recipe body containing **any** of these patterns is **excluded** with the matching reason (subject to the OS-attribute context rule above).

```yaml
project_markers:
  # Host/OS specific glue (always disqualifying, even inside [windows] — WSL paths
  # indicate the recipe is platform-mixed, not cleanly cross-OS)
  - pattern: '/mnt/[a-z]/'
    reason: WSL Windows mount path
    context: always
  - pattern: '\\\\wsl\$'
    reason: WSL UNC path
    context: always
  - pattern: '\bcmd\.exe\b'
    reason: cmd.exe invocation — host-specific glue
    context: always

  # Host-specific browser/tool launches — disqualifying when not in a [windows] or [macos]/[unix] split
  - pattern: '\bmsedge\b|\bchrome\.exe\b|\bfirefox\.exe\b'
    reason: host-specific browser invocation
    context: not_os_attributed
  - pattern: '\bopen -a (Safari|Chrome|Firefox)\b'
    reason: macOS-only browser launcher
    context: not_os_attributed
  - pattern: '\bxdg-open\b'
    reason: Linux-only browser launcher
    context: not_os_attributed

  # Databases not in the canonical .NET stack overlay (PostgreSQL, SQLite)
  - pattern: '(?i)\boracle\b'
    reason: Oracle DB — not in canonical .NET stack overlay
    context: always
  - pattern: '(?i)\bmssql\b|\bsqlserver\b'
    reason: SQL Server — not in canonical .NET stack overlay
    context: always
  - pattern: '(?i)\bmysql\b|\bmariadb\b'
    reason: MySQL/MariaDB — not in canonical .NET stack overlay
    context: always

  # Registry / org / company specifics
  - pattern: '\bghcr\.io/[^/\s${}()]+/'
    reason: hardcoded GHCR owner — org-specific (use a justfile variable instead)
    context: always
  - pattern: '\bdocker\.io/[^/\s${}()]+/'
    reason: hardcoded Docker Hub owner — org-specific
    context: always
  - pattern: '\bazurecr\.io'
    reason: hardcoded Azure Container Registry
    context: always

  # Tooling that isn't universally available
  - pattern: '\bclaude\b'
    reason: Claude Code CLI invocation — depends on a specific agent installation
    context: always
  - pattern: '\bcopilot\b'
    reason: Copilot CLI invocation — depends on a specific agent installation
    context: always

  # Hardcoded endpoints / ports in critical paths (probing is fine when parametrized)
  - pattern: 'https?://(?!localhost|127\.0\.0\.1|0\.0\.0\.0)[a-z0-9.-]+\.(com|ch|net|io|dev|internal)'
    reason: hardcoded non-localhost URL
    context: always
```

The `context` field controls when the marker applies:

- `always` — disqualifies regardless of recipe attributes.
- `not_os_attributed` — disqualifies only when the recipe has no `[unix]`/`[windows]`/`[macos]`/`[linux]` attribute. Inside an OS-attributed recipe, the host-specific tool is expected.

### Patterns that do NOT disqualify (explicit allowlist)

- `{{var}}` — any justfile variable interpolation. Variables are how projects parametrize; their presence is fine.
- `$VAR` / `${VAR}` — shell variable inside a bash/pwsh recipe body. Fine.
- `localhost` / `127.0.0.1` / `0.0.0.0` in URLs — local-only, every project has some of these.
- `pwsh` / PowerShell built-ins inside a `[windows]` recipe — see `windows_tools` above.
- Environment variable names that look project-specific (`InternalSettings__Foo`) — the name alone doesn't disqualify, but if it appears hardcoded in a recipe body (not as `{{var}}` or `$VAR`) it does. Flagged via `project_env_prefix` below.

```yaml
project_env_prefix:
  # Env-var names that, when literal in a recipe, mark the recipe as project-specific
  - pattern: '\bInternalSettings__'
    reason: project-specific app-internal configuration env var
  - pattern: '\bConnectionStrings__Default='
    reason: hardcoded connection string env — project-specific; if parametrized via {{var}} this is fine
```

## skip_recipes

Meta recipes to skip without classifying.

```yaml
skip_recipes:
  - default      # justfile convention — usually wraps `just --list`
  - show         # informational
  - open         # informational
  - list         # informational
  - print-*      # parametrized print recipe (justfile glob equivalent)
```

Recipes with the `[private]` attribute are also skipped (handled in SKILL.md Step 3).

## promotion_groups

How to group promoted recipes in the output section. Order matters — this is the order that ends up in the upstream patch.

```yaml
promotion_groups:
  - name: "Build & run"
    recipes: [build, watch, run, run-edge]
  - name: "Testing"
    recipes: [test, test-unit, test-coverage]
  - name: "Docker (Compose)"
    recipes: [docker-run, up, down, logs, rebuild]
  - name: "Quality"
    recipes: [lint, outdated, vuln]
  - name: "Versioning"
    recipes: [version, version-set, bump-major, bump-minor, bump-patch, bump-auto]
    note: "single source of truth — Directory.Build.props → <Version>"
  - name: "Release"
    recipes: [changelog, release-notes, release, release-auto, push-release, package]
  - name: "Cleanup"
    recipes: [clean]
```

Recipes not in any group that are promoted anyway go into a trailing "Other" group.

## disqualification_priority

When a recipe body matches both a `generic_tools` whitelist entry AND a `project_markers` pattern, `project_markers` wins. (Otherwise `docker compose -f {{oracle_dir}}/docker-compose.yml` would pass on "docker compose" and miss "oracle".)

The `context: not_os_attributed` markers are evaluated against the recipe's parsed attribute set, not the body content.

## intent_promotions

Recipes promoted by **name and intent**, not by body content. Upstream documents the canonical recipe name; the body is left to each project (host-specific, tool-specific, or destination-specific).

With justfile's `[unix]` / `[windows]` attributes, the cross-OS story is solved — these intent-promoted recipes ship as OS-attributed pairs upstream. The `upstream_note` strings describe the canonical split pattern so projects know what to ship.

```yaml
intent_promotions:
  - recipe: run-edge
    intent: "Start the frontend and open it in the developer's default/preferred browser (host-specific implementation)"
    group: "Build & run"
    upstream_note: "Body is host-specific. Ship as [unix] + [windows] recipe pair with the canonical name; bodies use per-OS launchers (Windows: pwsh + Start-Process msedge; macOS: open -a Safari; Linux: xdg-open)."

  - recipe: package
    intent: "Build a distributable deployment artifact (ZIP, tarball, container image, etc.) and deliver it to the project's drop location"
    group: "Release"
    upstream_note: "Body is project-specific (artifact format, drop location, signing). Standardize the recipe name; leave the body to each project. Use [unix] / [windows] pairs if the packaging pipeline differs by OS."

  - recipe: release-notes
    intent: "Generate user-friendly release notes for the current version using an AI/LLM tool"
    group: "Release"
    upstream_note: "Body is tool-specific (Claude Code, Copilot CLI, llm CLI, OpenAI, hand-rolled). Standardize the recipe name; leave the body to each project."
```

The skill emits these in the proposal under their assigned group with the `upstream_note` rendered as italics under the bullet, so reviewers see *why* the body isn't prescribed.

## notes for maintainers

- Heuristics are deliberately conservative. If you find the skill excluding something that should promote, **widen `generic_tools`** or add a `context: not_os_attributed` qualifier to the relevant `project_markers` entry rather than removing the marker outright.
- Patterns are anchored with `\b` word boundaries where possible to avoid substring false positives (`oracle` vs. `oracles`).
- `(?i)` inline flag for case-insensitive matches when the match space is text inside descriptions, not command names.
- The `windows_tools` allowlist applies **only** when a `[windows]` attribute is present on the recipe. Bare `pwsh` invocations in an un-attributed recipe still disqualify — that's a project-specific glue script, not a portable cross-OS recipe.
